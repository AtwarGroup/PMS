# إصدار التوظيف — جاهز للمراجعة، البريد مؤجل

نطاق الحزمة هو التوظيف فقط. قاعدة المقارنة: main عند 6fc6e43، ومخطط ودوال التوظيف المقروءة من اللايف يوم 28 أكتوبر 2026. لا تحتوي الحزمة بيانات حسابات أو مرشحين أو طلبات من التجربة، ولا إعداد الدخول التجريبي أو مفاتيحه.

## التغييرات

- مسار الاحتياج: الإدارة ← مراجعة مسؤول التوظيف والتوطين ← اعتماد صاحب الصلاحية ← الاستقطاب والمقابلات والاختيار ← العرض والقبول والمباشرة.
- التقييم والاختيار للمدير المباشر. مدير الإدارة يسجل تقييم المقابلة الثانية إذا طلبها؛ اعتماد العرض مستقل عن إعداده.
- نموذج لأطوار وآخر لمؤسسة لوازم الأبواب «تيرادور»، باختيار مسؤول التوظيف، مع حفظ الشروط داخل كل نسخة عرض.
- إقرار المرشح وتاريخ مباشرته المتوقع، نسخة قابلة للطباعة على A4، ومنع الرد على نسخة سابقة أو تكرار الإشعارات.
- سرية الراتب في تفاصيل الطلب وفي بيانات التهيئة، وسجل الإجراءات لمسؤول النظام فقط.
- إعداد أولي قابل للحفظ بثلاثة مسؤولين فقط. لم تعد الحقول المخفية لشؤون الموظفين والمالية تمنع بدء الوحدة.

## البريد المؤجل

البريد له مفتاح تشغيل مستقل `RECRUITMENT_EMAIL_ENABLED`. القيمة الافتراضية معطّل حتى لو كانت مفاتيح البريد العامة موجودة من بقية وحدات النظام. تبقى الموافقة والنسخة والإشعار الداخلي والطباعة متاحة. تستخدم الإدارة رابط المرشح يدويًا مؤقتًا. لا يعرض فشل البريد رسالة نجاح في الواجهة.

بعد انتهاء المستخدم من الربط، يُختبر الإرسال على التجربة إلى Jobs@tiradorstores.com فقط، ثم يفعّل المفتاح على اللايف. مرسل البريد المعتمد tasks@notify.tiradorstores.com. لا يُغيّر DNS الحالي أو مفاتيح بقية وحدات النظام. القبول لدى مزود البريد لا يعادل تأكيد الوصول؛ يلزم فحص حالة الرسالة الفعلية.

## خطوات النقل عند اعتماد النشر

1. التحقق من أن main لم يتغير بما يؤثر على التوظيف، وأخذ نسخة احتياطية من قاعدة البيانات والدوال الحالية.
2. تشغيل preflight.sql للقراءة فقط، ثم تطبيق upgrade.sql كاملًا؛ الملف محاط بمعاملة واحدة تتوقف عند أول خطأ. ينشئ جدول إعداد المسار وصندوق البريد، ويضيف حقول العرض ثم يحدث دوال التوظيف وصلاحياتها فقط. اختُبرت إعادة تطبيقه دون تعديل السجل التاريخي.
3. من إدارة المستخدمين والصلاحيات، تفعيل وحدة التوظيف للحسابات المقصودة. الأدوار المتفق عليها: أحمد منشي مسؤول التوظيف، احمد اليافعي صاحب الاعتماد، محمد باسنبل مراجع الاستثناءات. يظل طلب الاحتياج للمديرين/المشرفين ضمن الهيكل. هذه الحزمة لا تنسخ صلاحيات الحسابات التجريبية ولا تمنح الصلاحيات تلقائيًا.
4. حفظ المسؤولين الثلاثة في إعداد مسار التوظيف بالحساب الإداري الفعلي. تُشتق الإدارة والقسم والمدير من سجل الموظف؛ لا تُكتب بيانات تجريبية في الإعداد.
5. نشر ملفات الواجهة. نشر دالة recruitment-email مع تحقق الصلاحية داخل جسم الدالة، مع إبقاء RECRUITMENT_EMAIL_ENABLED غير مفعّل إلى انتهاء الربط.
6. التحقق من صفحة التوظيف بحساب مسؤول التوظيف والمعتمد والمدير المباشر، ثم فتح طلب اختبار واضح وعدم إرسال بريد أو عرض إلى مرشح فعلي خلال الفحص.
7. متابعة أخطاء الواجهة والدوال والصلاحيات. قبل أي تراجع يُحفظ ما أُنشئ من سجلات جديدة؛ لا تُحذف أعمدة أو بيانات لتراجع آلي غير آمن.

لا يوجد ترحيل لبيانات التجربة إلى اللايف، ولا تحديث للأسطول أو تقنية المعلومات أو بقية الأنظمة.

## التحقق

- npm run test:recruitment:db: اختبارات الأساس المعزولة للموافقات والاستثناءات والدفعات والمستندات والتقويم والتذكيرات.
- npm run test:recruitment:release: تطبيق تحديث المخطط على تعريفات اللايف الحالية، إعادة التطبيق، حفظ السجل السابق، تهيئة الأدوار الثلاثة، ثم دورة كاملة بالبيانات المصطنعة وصلاحيات صندوق البريد.
- tests/*.mjs: فحوص الانحدار العامة، دون تعديل بيانات أي بيئة.
- جميع اختبارات النقل تستخدم PostgreSQL معزولًا؛ لا يعني نجاحها تطبيق التحديث على اللايف. اختبار وصول البريد الحقيقي مؤجل.
